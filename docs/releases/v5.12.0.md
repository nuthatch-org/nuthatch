Nuthatch 5.12.0 widens what an address-history nest answers in two places: off a loopback bind,
and for an account with code on the chains whose history is proved by the balance. There is no
storage migration, and no nest's NID, registry hash or sealed segment changes.

## Off a loopback bind

A nest lends its operator's RPC only on a loopback bind, so one behind a reverse proxy, or reached
from another container, refused `proxy/eth_blockNumber` and `account/balance`. A client that reads
the head before every range, as Etherscan-shaped readers do, failed every sync against it.

Off loopback now (#2405):

- `proxy/eth_blockNumber` answers the nest's own finalized head, and `NUTHATCH_INCOMPLETE` before
  the first one. Nothing is lent.
- `account/balance` and `account/balancemulti` are read from the RPC only when every address asked
  is watched, the same line a `txlistinternal` lookup by `txhash` already draws. Any other address,
  or none, is refused.
- Every other `proxy` and `logs` call is still answered on loopback only.

## Token transfers for an account with code

On Optimism, BNB Smart Chain, Gnosis, Polygon, Base and Arbitrum a nest proves an account's
transactions by its balance, which another account's code can spend. An account with code, a
contract or one with EIP-7702 delegated code, was therefore refused for every action from the block
it gained code. Its token transfers come from log filters and need no such proof.

`txlist` and `txlistinternal` are still refused from that block. `tokentx`, `tokennfttx` and
`token1155tx` are now served across it and followed to the head (#2406). A smart-contract wallet's
token history is complete; its plain and internal transactions still come from another source.
Ethereum mainnet is unchanged.

## Compatibility and upgrade

Replace the binary and restart. A 5.11.1 store is used as it is. A nest that already marked an
account with code backfills that account's token transfers from the mark on its next poll.
