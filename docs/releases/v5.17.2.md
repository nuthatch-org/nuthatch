Nuthatch 5.17.2 makes catalogue reads on a wide nest fast and much smaller. There is no storage
migration, and no NID, registry hash or sealed segment changes.

## Listing a nest's tables no longer costs a read of every segment

A query that reads `information_schema` (`.tables` and `.schema` in the REPL, an agent discovering
the schema, a BI tool connecting) defines every table in the nest. Each definition read the footer of
every sealed segment, kept one copy of its schema per file, and resolved every file's full path, and
the server repeats all of it whenever the tip seals (#2669). On the ENS nest, 189,129 segments in 157
tables, that was 5.6 to 7.0 s per read and 856 MB peak, against 0.37 s for `SELECT 1`; over HTTP
while ingesting, one such read reached the 29 s budget.

A segment's footer is now read once per process and shared by every session, one copy is kept per
distinct schema, and each segment directory is resolved once. Measured the same way, a repeat read
takes 1.32 to 1.42 s and peaks at 456 MB. The first read after a restart still reads every footer,
about 5.6 s on that nest. Answers are unchanged.

Who is affected: any nest with many sealed segments, and most of all one with many tables. Ordinary
queries that name their tables gain less, since they already defined only what they read.

## Compatibility and upgrade

Replace the binary and restart. A 5.17.1 store is used as it is.
