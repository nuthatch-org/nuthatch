Nuthatch 5.15.0 adds the embeddable engine of RFC-0077: nuthatch's core as a WebAssembly module, a
separate artefact on this release, opt-in and off by default. For a binary user nothing changes. The
binary stays the main way to run nuthatch, and everything it did in 5.14.1 it does the same way here.
There is no storage migration, and no nest's NID, registry hash or sealed segment changes.

## For a binary user, nothing changes

Code the engine shares with the binary moved from `src/` into the `nuthatch-core` crate, which the
binary calls (#2537, #2538, #2540, #2541, #2542): the nest's part of `nuthatch.toml` and the chain
registry, the entity binding and `/sql` error hints, the warm-start rebuilds of the views, entities and
factory children, the seed's checks, and what `/sql` binds for labels and children. The moved code is
the same code, with the same messages. At each step:

- every subcommand's `--help`, two levels deep (60 pages), and the files `nuthatch init --abi` writes
  for mainnet and Arbitrum One were byte-identical before and after;
- `cargo tree` listed the same crates, versions and features, and `Cargo.lock` gained only edges from
  `nuthatch-core` to crates the binary already used, at the versions it already used;
- the whole suite passed, 2,879 tests at S5, the last slice to run all of it, with the segment-hash pins, the reorg suites,
  `e2e_warm_restart` and `bench_restart_mounts` unchanged and green.

Building the binary needs no wasm toolchain, and nothing in `embed/` is in its dependency graph. The
`eth_getLogs` requests a node makes are the same JSON: the RPC client can now send topics 1 to 3, and
only the engine sets them.

Two messages read differently, because they called RFC-0041 §5.3's warm-restart seed unimplemented,
and it is implemented (#2534, in #2540):

- An entity left unavailable after a restart now says its seed from the sealed segments and hot tail
  did not complete, that the log says why, and that the next restart seeds it again. It used to say the
  seed was not implemented and to re-index the nest.
- `--seal-direct` with authored entities is still refused, and the refusal now ends "an entity is
  rebuilt from sealed history only when a nest restarts (RFC-0041 §5.3)".

## The embeddable engine

The engine is the event nest of the binary, compiled to `wasm32-unknown-unknown` as a plain core
module: no WASI, no wasm-bindgen, no component model. A host drives it through a small interface and
performs every request it makes, to the RPC, mirror or storage the host chose; the module reaches
nothing itself. It is for data that belongs to one user on one device: a wallet, rotki, a dapp's
frontend, `/play`. When many users share one view, run the binary.

It runs a nest's `nuthatch.toml` on the chain's registered policy, with factories, labels and flags;
`entities.toml` and `views/*.sql`; reorgs; sealing; `/sql` and the node's HTTP answers. It can open a
published nest from a mirror, checked as `nuthatch seed` checks it, and, given a light client's
finalized block, seal only what hashes down to it. Its answers are the node's: CI holds the same
module file to the binary's pinned answers, segment hashes and balances, including after the host is
killed mid-follow and reopened, and across 13 nest shapes the binary's own tests write out.

- **Interface: `abi: 1`**, specified in the README attached to this release. `nh_abi` reports
  `{"abi": 1, "capabilities": ["events"], "storage": ["bytes", "host"], "engine": "5.15.0"}`. The
  shapes of every export and import are pinned, and a change to any of them changes the version.
- **Tested hosts**: Node over files, wasmtime 48 from Rust over files, and headless Chrome on OPFS, all
  in CI on every change to the engine. Brave was run by hand for mirrored nests and for the Lodestar
  page below.
- **Untested**: Safari, Firefox and phones.

The worked example is a "verify it locally" card for a Lodestar profile, built on a branch and not
deployed: it indexes one wallet's Graph delegations and curation on Arbitrum One in the browser and
compares every figure with the server's at the same block. Seven addresses, 409 figures, none
differing (RFC-0077 §18).

### Limits

- **Compile once, then cache.** The module is about 34 MB. Compiling it peaks at 1.3 to 1.9 GiB of
  memory, once, whatever the compiler or thread count; a precompiled module loads in under 10 ms and a
  run stays under 200 MiB. A host that must compile it at every start in phone-sized memory, or in a
  128 MB isolate, cannot run it. Browsers cache compiled modules themselves.
- **Size**: 5.27 MB brotli. The release job refuses a module over 5.5 MB.
- **It trusts its RPC on Arbitrum.** The verified head is a mainnet light client's; nothing verifies an
  Arbitrum block, and an RPC that leaves a log out is not caught.
- **One instance runs one nest**, single-threaded, in at most 4 GiB of linear memory that never
  shrinks.
- **The address build is not shipped.** RFC-0074's address history as a module, the build rotki would
  embed, waits on RFC-0074 S2.

### The assets

| Asset | What it is |
|---|---|
| `nuthatch-events.wasm` | the module |
| `nuthatch-events.wasm.sha256` | its SHA-256 |
| `nuthatch-events-README.md` | `embed/README.md` at this tag: the interface, what a host needs, the reference hosts |

The release job builds the module from this tag and gates that exact file before attaching it: its
imports, the size ceiling, the pinned interface, `nh_abi`'s version, and RFC-0075 S3's and S5's answers
in Node and wasmtime, fresh and killed mid-follow. To check a download:

    shasum -a 256 -c nuthatch-events.wasm.sha256
    gh attestation verify nuthatch-events.wasm --repo nuthatch-org/nuthatch

The README's relative links point into the repository at `embed/`; read it there at the `v5.15.0` tag
for working links.

The design is [RFC-0077](https://github.com/nuthatch-org/nuthatch/blob/v5.15.0/docs/rfcs/0077-the-embeddable-engine.md),
with each slice's measured outcome in §12 to §18. The longer account is
[Nuthatch as a wasm blob](https://www.nuthatch-indexer.com/blog/nuthatch-as-a-wasm-blob/).

## Compatibility and upgrade

Replace the binary and restart. A 5.14 store is used as it is: nothing in storage changes, and no NID,
registry hash or sealed segment changes. `decode`, `seal`, `scaffold` and `identity` are untouched
since 5.14.1, and the segment-hash pins pass unedited. Writers and followers of 5.14 and 5.15 work
together in either direction, as nothing in the feed changed.

The engine is a separate download. An operator who does not fetch it has nothing to do.
