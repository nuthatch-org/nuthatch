Nuthatch 5.18.1 fixes two places where 5.18.0 gave an answer that was not true: the engine named a
different nest from the node, and address history called a range incomplete that it will never
cover. There is no storage migration, and no NID, registry hash or sealed segment moves on a node.

## Upgrade guidance

Replace the binary and restart. A 5.18.0 store is used as it is.

- **The embeddable engine** (`nuthatch-engine.js`, `nuthatch-events.wasm`): upgrade it if you hand it
  a nest directory, for `verify` or otherwise. 5.18.0's engine disagrees with a node on the NID of
  every nest made by 5.18.0's `init` or `add`.
- **Address history and validator clients**: a client that matches on the `NUTHATCH_INCOMPLETE`
  prefix for a range outside the configured history should match `NUTHATCH_UNSUPPORTED` instead. The
  text after the prefix is unchanged, so rotki, which reads `history starts at block N`, needs nothing.
- **Log scrapers**: the `API live on` line now prints the address the node bound.

## The engine names the nest the node names

Since 5.18.0, `init` and `add` write a `.gitignore` into every nest, and the node leaves it out of
the NID. Only the node did, though (#2822): the engine given a directory, the time-lapse crate and
the nest builder hand every file they hold to `nuthatch-identity`, which counted it. So for any new
nest the engine computed a NID the node does not report, and `verify` against that node saw another
nest. The rule now lives in `nuthatch-identity` itself, so every caller drops `.gitignore` at any
depth (#2825). The node's NIDs do not move; the pinned identities of fixed nests still hold.

The nest builder at `/play/build.html` was not affected, because it pins a scaffold from before
5.18.0.

## A range this nest will never cover is unsupported, not incomplete

An address-history request starting before `[address_history] start_block`, or with either bound
past `end_block`, answered `NUTHATCH_INCOMPLETE` (#2823). That status means the nest has not covered
the range yet and a client may ask again; the configuration means this nest never will. Those
requests now answer `NUTHATCH_UNSUPPORTED`, with the same text (#2824), and so do validator requests
past `end_block` (#2826). The validator endpoint already answered unsupported before its first
proven block, so the two now agree.

Who is affected: a nest with `start_block` or `end_block` set under `[address_history]`, and only
for requests outside that range.

## The bound address in the startup log

`API live on http://...` now prints the address the listener bound rather than the one configured,
so a node started on port 0 reports the port it took (#2819). For any other `--listen` the line reads
as before.
