Nuthatch 5.19.0 lets an address-history nest on Gnosis list the transactions of a contract, and
fixes a regression in 5.18.0 that could leave a dense window unrecorded for good. There is no storage
migration, and no NID, registry hash or sealed segment moves.

## Upgrade guidance

Replace the binary and restart. A 5.18 store is used as it is.

- **Address history on any chain**: upgrade if a window has been failing with `timed out` since
  5.18.0. It will be read in narrower spans and recorded.
- **Address history on Gnosis, watching a contract or an EIP-7702 delegated account**: `txlist` and
  `txlistinternal` stop answering `NUTHATCH_UNSUPPORTED` for it and are backfilled from the block it
  was refused at, if your trace RPC serves `trace_filter`. If it does not, nothing changes. Expect the
  backfill to cost trace calls: see the figures below before pointing it at a metered endpoint.
- Every other nest: nothing to do.

## A span that timed out is narrowed again

5.18.0 stopped treating a rate limit as a reason to shrink a window (#2730). The same change made
every other classified failure fatal to its span, and a transport timeout is one of those, so an
`eth_getLogs` or `trace_filter` span the provider ran out of time on failed its whole window instead
of being asked again in halves, as it had been through 5.17 (#2833). On a chain read by the balance
residual a window cannot go below 16,384 blocks, so a dense one was retried at the same width every
few polls and never recorded.

Measured on Gnosis with GraphOps on 2026-11-11: `eth_getLogs` over blocks 32345760 to 32362143 for
one account, 7,562 transfers in one topic position, answered in 7.9 s alone and timed out at 20 s with
the window's other calls in flight. It failed twice, 6.5 minutes apart, at the same width. The first
4,096 blocks of it answer in 0.1 s.

A transient failure whose text says `timed out` narrows the span again (#2834). An endpoint that
refuses the connection still fails on the first call, and one block that times out still fails.

## On Gnosis, an account with code is traced

Gnosis is one of the chains whose transactions nuthatch finds from an account's nonce and balance
rather than by `trace_filter`. That proof holds only for an externally owned account: another
account's code can spend a contract's balance. So a contract, or an account with EIP-7702 delegated
code, answered `NUTHATCH_UNSUPPORTED` for `txlist` and `txlistinternal` from the first block it had
code (#2835).

Gnosis's providers do serve `trace_filter`, so where the balance cannot prove an account, the nest
now finds its transactions the way it does on Ethereum (#2836). A trace endpoint that answers that
it has no such method leaves the account refused, as before. Markers written by an earlier binary are
dropped when the nest opens, so an account refused under 5.18 is backfilled from the block it was
refused at. The other residual chains are unchanged.

A traced account's history rests on the trace RPC's answer; there is no balance to check it against.

What it costs, measured 2026-11-11 with one address in the filter:

| Endpoint | Widest `trace_filter` span | Time |
|---|---|---|
| Alchemy | 20,000 blocks | 11.7 s |
| GraphOps | 16,384 blocks (stated) | 11.5 s per 2,000 |
| rpc.gnosischain.com, rpc.gnosis.gateway.fm | 100 blocks (stated) | 2.0 to 3.7 s |

With GraphOps as `--rpc` and Alchemy as `--trace-rpc`, a proxy contract's first 500,000 blocks,
32100000 to 32600000, were recorded at about 16,000 blocks per 10 to 15 s: 6,367 `txlist` rows, the
first its own creation. On the keyless endpoints the same range is 5,000 calls for each of the two
directions.

**How it was checked.** No explorer serves Gnosis's account API without a paid key any more, so
there is no Etherscan parity run for this. Instead, 4,000 block bodies, 32304000 to 32307999, were
read from rpc.gnosischain.com and searched for transactions to or from the contract: 123, the same
123 hashes the nest lists for those blocks. `txlistinternal` answered no rows for the range and was
compared against nothing.

## A stated limit the provider has already exceeded is not believed

Address history shrinks a window to the limit a provider states in its refusal. Alchemy's Gnosis
`trace_filter` refuses a span that ran past about 15 s with "limited to 100 blocks", having served
20,000 a moment before. Taken at its word, that pinned the window at 100 blocks for the life of the
process: 200 times the calls.

A stated limit below a span the same window has already been served is now ignored, and the refused
span is halved instead (#2836). A limit stated before anything wider was served is still taken as
given, which is why the Gnosis trace window starts at 10,000 blocks rather than 100,000. The cost
falls on a provider that really does lower its limit after serving more, as Alchemy has done on
Optimism from 5,000 to 100: the window reaches the new limit in about six refusals instead of one.
